# CrossWMS / CDFKnow 整体分析与下一步开发方向（2026-08-10）

> 承接《2026-08-09 重新分析》（停在 `refactor/staff-dedup-mcp` / v1.7.187）。
> 本报把视角从"整合是否稳固"升级为"整合后往哪走"，并纳入 08-09 之后 `main` 的新进展。
> 所有结论基于 2026-08-10 实测：git status / git log / git diff --stat / 既有交付物。

---

## 0. 一句话结论

**软件已越过"整合阵痛期"，进入"能力深化 + 质量门禁固化"阶段。** 双套 UI 收敛、git 瘦身、CI/typecheck 加固已收口；当前在飞的是 AI 对话框重构、仓库员工能力整合、WMS 样式统一与 DMG 打包精修。下一步最该做的不是继续加功能，而是 **(1) 把特性分支合入 main 收口、(2) 拍板并推进 P2-1 API 契约统一、(3) 固化 engine 测试门禁、(4) 建立与 OpenClaw 上游的长效同步机制**。产品主线聚焦**数字员工能力闭环**。

## 2. 整体成熟度评估（四象限）

| 象限 | 评级 | 判断 |
|---|---|---|
| **架构** | 🟡 中等偏稳 | Swift+WKWebView 外壳 + React/MUI 前端 + Express/SQLite 后端；v9.0 统一 `streamExecutor`；MCP/plugin/builtin 三类工具齐备。最大隐患是 `server/engine` 为 **272 万行 OpenClaw 硬分叉**，抽样 55% 已改 / 33% 独有 / 12% 同上游 → 与上游已显著分叉。 |
| **能力** | 🟢 较完整 | 执行策略、技能系统、自动化、多供应商模型管理、数字员工(StaffDeck)、跨境 WMS 域页面均已落地。近期在补"仓库员工能力整合 + WMS 能力接入"，能力面在扩。 |
| **质量 / 工程** | 🟡 关键债未清 | tsc/CI 已加固；但 API 契约 893/1064 处裸返回、engine 测试覆盖率门禁依赖"CI 先 build openclaw"仍未固化、API client/markdown 各 2 份重复实现。 |

**总评**：技术底座可用、主线清晰，但**工程质量债（契约一致性 + 测试门禁）与上游分叉风险**是制约它从"能跑"走向"可规模化交付"的两块短板。

## 3. 关键风险与阻塞

1. **上游同步悬空（高）**：`sync/openclaw-2026-08-04` 含 401 个上游新文件，自 08-04 起**未审阅合入**。33% 独有引擎代码使手动 merge 风险高，长期不碰会越漂越远。
2. **特性分支未收口（中）**：`refactor/staff-dedup-mcp` 已完成代码级整合，但**仍等"真机 e2e 后合 main"**。当前 main 已另起炉灶推进对话框重构，两线并行易产生冲突与重复劳动。
3. **P2-1 API 契约（中，阻塞于决策）**：基建 `respond.ts` 已就位，但全量 105+ 路由采用统一 envelope **卡在"范围 + 错误形态"两点拍板**，两年没推。
4. **测试门禁静默漏覆盖（中）**：主 `vitest.config.ts` 仍含 `server/engine/**` 且无 helper 别名 → 主套件中 ~30 个 engine 测试解析失败；`test:engine` 又依赖 openclaw/dist 先 build，否则覆盖率缺口无人发现。
5. **在飞改动未提交（低）**：main 上有 modelSelector / TopBarChatInput / DMG / CSS 等 10 处未提交精修，属正常开发态，但应尽早按铁律 `git commit --no-verify`（先 tsc 0 error）收口，避免与合分支冲突。

## 4. 下一步开发方向（优先级路线图）

### P0 — 收口与防回归（本周内）
| 动作 | 退出标准 |
|---|---|
| 把 `refactor/staff-dedup-mcp` 的真机 e2e 结果落档，合入 main（先解决与 510b2f07 的对话框重构冲突） | main 含整合收口且无 tsc 错误；`/staff`→`/staffdeck` 重定向仍成立 |
| 当前 10 处在飞改动按铁律提交：`npx tsc --noEmit -p tsconfig.json` EXIT=0 → `git commit --no-verify`（精确列文件名） | 脏树归零，无 `git add -A` |
| 锁死 git 瘦身成果：CI 加 `.git` 体积门禁（>150M 告警），防 `server_dist/coverage/report` 回胖 | CI 体积检查通过 |

### P1 — 工程质量硬化（本迭代）
| 动作 | 退出标准 |
|---|---|
| **拍板 P2-1**：两周内定下"全量范围（先核心 105 路由还是全 1064）+ 错误形态（BizCode 4xxxx/5xxxx 落地方式）"，出一份执行清单 | 决策文档 + 路由分批表 |
| 按清单推进 `respond.ts` 统一 envelope，先核心路由，配契约测试 `npm run test:contracts` | 核心路由 100% 带 `code`，契约测试绿 |
| **固化 engine 测试门禁**：CI 流程改为 `build openclaw` → `test:engine`（带 coverage）→ 主套件移除 `server/engine/**` | engine 覆盖率可见且不静默丢失；主套件 0 解析失败 |
| 合并 2 份 API client、2 份 markdown 渲染近亲副本 | 单实现，调用方统一，无重复包 |

### P2 — 上游与产品深化（下迭代起）
| 动作 | 退出标准 |
|---|---|
| 建立**上游同步长效机制**：定频（如每月）把 `sync/openclaw-*` 的 401 文件做差异评审，只合"非冲突的通用修复"，冲突部分走适配层 | 同步 runbook 文档 + 首次增量合入验证 |
| **数字员工能力闭环**：以"仓库员工能力整合 + WMS 能力接入"为样板，沉淀"员工 ↔ 技能 ↔ 工具"的注册/发现/权限标准，支撑多租户与技能市场 | 可演示：新员工接入 ≤ 半天；能力清单可被 LLM 自动发现 |
| `components/staff` 重命名为 `ui-kit/` 或 `shared/`（名不副实整洁项） | 引用全部更新，无断链 |

### 可暂缓（记录但不排期）
- 去 iframe 方案（已有《数字员工去iframe方案建议》）：iframe 当前是唯一稳定实现，去 iframe 收益不明、风险高，**维持现状**。
- 回退 engine 为 submodule：抽样 33% 独有代码，回退会丢失关键定制，**不回退**。

---

## 5. 建议的"单一最重要下一步"

> **优先收口 `refactor/staff-dedup-mcp` 合入 main，并同步把在飞的 10 处对话框/能力改动提交。** 
> 理由：当前 main 与特性分支两条线并行推进，越晚合越易冲突；整合收口是后续所有质量债（P2-1、engine 门禁）的前置，先把"代码级事实"钉死，再谈硬化。合入后立刻启动 P2-1 决策——它是唯一卡在"人拍板"而非"技术难"的阻塞项，决策成本最低、杠杆最高。
