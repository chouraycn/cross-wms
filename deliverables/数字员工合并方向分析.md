> 日期：2026-08-03 · 分析结论基于真实代码（附路径行号）

## 0. 结论先行（给你一句判断）

**你的怀疑成立，但需修正范围：**

- ✅ **执行引擎层：数字员工已经 100% 复用核心，没有重复。** 数字员工对话最终走到核心 `executeChat`（`server/engine/streamExecutor.ts`）→ `ReActExecutor`（`server/engine/reactExecutor.ts`），没有任何"第二套 ReAct 循环"。
- ⚠️ **重复集中在三层**：① 数据访问层（`sd_*` 自建表 + `server/dao/staff/` 20+ 个 DAO 与核心 DAO 平行孪生）；② 工具层（`sd_tools` 的 HTTP 工具与核心 `web_api_call` 功能重叠）；③ 前端层（三套并行聊天 UI）。
- 🎯 **合并方向本质**：把数字员工从"一套自带存储/工具/前端的平行系统"收敛为"**核心引擎之上的一层 Agent 配置（人设 + 绑定 + 租户隔离）**"，删掉重复实现，保留领域特有数据。

### 1.3 工具层 —— HTTP 工具与核心重叠 🔴

- 核心 `web_api_call`（`toolRegistry.ts:700-705`）：外部 REST 调用，域名白名单 + `fetchWithSsrFGuard`。
- staff `http_tool_*`（`staffHttpToolBridge.ts`，`sd_tools` `tool_type='http'`）：租户/员工级可配置 URL/方法/鉴权头。
- **重叠点**：两者都是 SSRF 防护下的外部 HTTP 调用。差异仅在"可配置粒度"。建议核心 `web_api_call` 支持从工具表读取可配置条目，删 `staffHttpToolBridge` + `staffToolDao` 的 http 部分。

### 1.4 前端层 —— 三套并行聊天 UI 🔴

1. 核心聊天 UI：`src/components/CrossWmsChat`、`src/components/CDFChat`（MUI）。
2. 主程序内 staff 页（MUI，独立重写）：`src/pages/staff/chat/ChatPage.tsx` 用本地 `./components/ChatHeader`/`ChatEmptyState`/`ChatDialogs`，**0 处 import 核心聊天组件** → 与核心聊天 UI 不共享代码。
3. 嵌入的 StaffDeck-main 前端（iframe，shadcn/Tailwind，独立技术栈）：`dist/staffdeck-app`（来自 `StaffDeck-main/frontend-enterprise`），`index.ts:696` 静态托管 + iframe 嵌入。

> 注：按既有铁律 `src/pages/staff/*` 本就是"兜底"，真实数字员工前端是 iframe。但兜底页仍重复实现了聊天交互，应复用核心聊天组件或直接收敛到 iframe。

## 2. 合并方向（核心建议）

**总方针：数字员工 = 核心引擎之上的"Agent 配置层"，删重复、留领域。**

```
                  ┌─────────────────────────────────────┐
   数字员工前端    │  iframe(StaffDeck) / 或复用核心Chat    │
   (渠道/人设UI)   └───────────────┬─────────────────────┘
                                  │ agent_id / tenant_id
   ┌──────────────────────────────▼──────────────────────────────┐
   │  数字员工"配置层"（保留，薄）                                  │
   │  sd_agent_profiles · sd_agent_*_bindings · sd_tenants/users    │
   │  sd_general_skills(物化桥) · sd_human_handoff · sd_*_feedback  │
   │  sd_agent_events(trace) · sd_stream_jobs · sd_agent_usages    │
   └──────────────────────────────┬──────────────────────────────┘
                                  │ 复用
   ┌──────────────────────────────▼──────────────────────────────┐
   │  核心引擎（已共享，不动）                                      │
   │  executeChat / ReActExecutor / toolRegistry / McpClientManager │
   │  memory_entries · mcp_servers · user_skills · cron_jobs ·      │
   │  sessions/messages · models.json · fetchWithSsrFGuard          │
   └───────────────────────────────────────────────────────────────┘
```

**删除（重复实现）：** `server/dao/staff/staffMcpServerDao.ts`、`staffMcpClientManager.ts`、`staffHttpToolBridge.ts`(+`staffToolDao` http 段)、`staffSkillDao`/`staffSessionDao`/`staffChatDao`/`staffMemoryDao`/`staffScheduledTaskDao` 中与核心同构的部分。

**合并（落到核心表，加 `tenant_id`/`agent_id` 列）：** `sd_mcp_servers`→`mcp_servers`、`sd_sessions`/`sd_messages`→核心会话表、`sd_memories`→`memory_entries`、`sd_scheduled_tasks`→`cron_jobs`、`sd_skills`→`user_skills`。

**保留（领域特有，核心无等价）：** `sd_tenants`/`sd_users`、`sd_agent_model_bindings`/`sd_agent_resource_bindings`、`sd_agent_skill_branches`(+versions)、`sd_general_skills`（物化桥接关键）、`sd_human_handoff_requests`、`sd_message_feedback`/`sd_skill_feedback`、`sd_agent_events`、`sd_ui_configs`/`sd_persona_configs`、`sd_stream_jobs`、`sd_mock_orders`、`middleware/staffAuth.ts`。

## 3. 合并分支方向（Git 策略）

当前 staff 代码**已在 `main`**（无独立 staff 特性分支待合并），故"合并分支方向"= **重构分支策略**。建议保持 `main` 稳定，按阶段开 feature/refactor 分支，经现有质量门（pre-commit + `test:e2e:api` + Playwright）PR 回 `main`：

| 分支名 | 范围 | 风险 | 预计收益 |
|---|---|---|---|
| `refactor/staff-dedup-mcp` | `sd_mcp_servers`→`mcp_servers`(+列)，删 `staffMcpServerDao`/`staffMcpClientManager` | 低 | 删 ~2 文件，消双份 MCP 真相 |
| `refactor/staff-dedup-http-tools` | `sd_tools`(http) 并入 `web_api_call` 配置驱动，删 `staffHttpToolBridge` | 低 | 消工具层重复 |
| `refactor/staff-dedup-skills` | `sd_skills` 对齐核心技能体系 | 中 | 消技能 CRUD 平行孪生 |
| `refactor/staff-session-store` | `sd_sessions`/`sd_messages` 并入核心会话表 | 中 | 消存储隔离冗余（注意：当前"存储隔离"是有意设计，合并需把 `agent_id`/`tenant_id` 落到核心表） |
| `refactor/staff-frontend-dedupe` | `src/pages/staff` 聊天页复用核心 `CrossWmsChat` 组件，或收敛到 iframe | 中 | 消第三套聊天 UI |

> 高优先做前两个（复用度最高、成本最低、立即可削减"双份真相"风险）。`session-store` 与 `skills` 因涉及"有意的存储/版本隔离"，单独成支、带数据迁移脚本与回滚方案。

## 4. 执行纪律（来自项目铁律，勿破）
