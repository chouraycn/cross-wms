## 2. 端到端测试（核心硬证据）

| 文件 | 结果 | 说明 |
|---|---|---|
| `inbound.test.ts` | ✅ 全过 | WMS 入库路由后端集成正常 |
| `inventory.test.ts` | 🟡 5/6 过 | `GET /:id` 不存在→404 通过；**`PUT /:id` 不存在→400（期望 404）失败** |
| `chat.test.ts` | 🟡 2/3 过 | queue-status / queue-cancel 通过；**`POST /api/chat` 超时 30s** |

**两个失败的解读（都不是我引入的回归）：**

1. **`POST /api/chat` 超时**：测试期望"发 POST 立即拿到 200 + SSE 连接"。但真实路由会启动**完整 LLM 对话流**（需要模型后端 + key），测试环境无 key → 挂起超时。这是**测试用例设计缺陷**（应 mock LLM 或只验 SSE 握手），不是产品 bug。我未改动后端 chat 路由。
2. **`inventory PUT` 400 ≠ 404**：同一资源"不存在"在 `GET` 下返回 404、在 `PUT` 下返回 400。**这正是 P2-1「API 契约倒挂」的微观实锤**——not-found 状态码随 HTTP method 漂移，前端若按统一 `code` 处理会踩坑。

## 3. P2-1 被 E2E 证实（不是假设）

前报把"API 契约倒挂"列为待办。本轮 e2e 直接抓到一个实例：

```
inventory 路由：
  GET  /api/inventory/nonexistent  → 404  ✅
  PUT  /api/inventory/nonexistent  → 400  ❌（测试期望 404）
```

同一"资源不存在"，不同 method 返回不同状态码。这与前报"envelope 覆盖率 staff 21/23 vs 主程序 15/121"是同一类问题——**契约不统一**。P2-1 的必要性从"分析推断"升级为"测试证伪"。

## 5. 结论

1. **前报的"落地"经得起测试**：端到端 **86 测试 / 84 通过（97.7%）**——API 批次（inbound/inventory/agents/memory/smoke 79 测 77 过）+ UI 批次（staff.spec 7 测 7 过）。证明五项优化的后端影响面（WMS 路由、chat 路由挂载、staff API 契约）与前端健康度（应用可加载、路由可达）**均无回归**。
2. **品牌/构建/前端类型三层已验证闭环**；UI 收敛与 WMS 导航"代码在、应用健康、渲染细节待真机精确验"。
3. **P2-1 从假设变实证**——`inventory PUT 400≠404` 是契约不统一的活样本，优先级应上调。
4. **唯一硬阻塞仍是脏树**：git 瘦身（634MiB→预期 ~65MiB，隔离副本已验证 91% 降幅）与 P2-1 对齐都要求工作树干净。用户 commit 28 处改动后，两项可立即执行。
