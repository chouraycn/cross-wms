# 数字员工去 iframe 嵌入方案建议（保持现状前提下）

> 目标：在**不改变数字员工功能形态、保持 StaffDeck 子模块独立开发、后端复用主引擎不变**的前提下，仅替换"嵌入容器"技术，去掉当前 `<iframe>`。
>
> 现状机制：StaffDeck 前端（shadcn/Tailwind，构建在 `dist/staffdeck-app/`）由主应用 `<iframe>` 加载，`StaffDeckPortal` 把 iframe 提升到路由树外常驻（去双击卡顿）；前后端经 **postMessage** 通信；iframe 是数字员工**唯一**复刻实现。

---

## 0. iframe 当下提供的价值（去之前要权衡）

iframe 不是技术债，它提供了**强隔离**：
1. **CSS 沙箱**：主应用 MUI 与 StaffDeck Tailwind 全局样式互不污染（这是最大的隐性价值）。
2. **JS 沙箱**：StaffDeck 的全局变量 / 事件监听不污染主应用 window。
3. **崩溃隔离**：StaffDeck 运行时报错不影响主应用渲染。
4. **独立 window / history**：天然避免路由、滚动、焦点耦合。

→ 任何"去 iframe"方案都要**补偿这四项隔离的缺失**，否则会引入 MUI↔Tailwind 样式冲突、上下文耦合等新问题。

---

## 1. 替代方案对比

| 方案 | 机制 | 隔离度 | 工作量 | 主要风险 |
|---|---|---|---|---|
| **A. Module Federation（模块联邦）** | StaffDeck 作为 remote 暴露 `<StaffDeckApp/>`，主应用 host 运行时拉取并挂载到**同一 React root** | 弱（共享 React 运行时） | 中 | 主/子 React 版本必须对齐；运行时耦合 |
| **B. ESM 组件库（推荐首选）** | StaffDeck 构建为导出 `<StaffDeckApp/>` 的 ESM 包，主应用 `import` 后直接渲染到 `#staffdeck-mount` | 弱（无 DOM 隔离） | 中-高 | **Tailwind 全局样式需作用域化**；StaffDeck 需去 HTML 壳改为纯组件 |
| **C. Web Component（Shadow DOM）** | 把 StaffDeck 包成 `<staff-deck-app>` Custom Element，可选 Shadow DOM | 中（Shadow DOM 样式隔离） | 中 | 双 React 实例开销；postMessage→属性/事件的通信改造 |
| D. 反向嵌入（主应用壳化） | 不适用 | — | — | 推翻"子模块独立"约束，违背前提 |

---

## 2. 推荐

- **必须去 iframe 且保持子模块独立 → 选 B（ESM 组件库）**：最贴合"子模块独立开发 + 后端复用"，去掉 DOM 孤岛后共享同一 React tree，通信可保留 postMessage 或升级为 props/Context 直传。
- **多团队独立部署 / 版本解耦诉求强 → 选 A（Module Federation）**：适合 StaffDeck 与主应用发版节奏不同步。
- **想保留样式隔离又去 iframe → 选 C（Shadow DOM）**：接受双 React 实例的成本换回样式沙箱。

> **默认建议：除非有明确诉求（如消除 iframe 双击/预热卡顿、统一鉴权上下文、需要深度链接/SEO、或 StaffDeck 需直接读写主应用状态），否则保留 iframe。** iframe 的强隔离在"主应用 MUI + 子应用 Tailwind"这种异构 UI 栈下尤其值钱。

---

## 3. 迁移步骤（以方案 B 为例）

1. **StaffDeck 去壳**：入口从"挂载到 `document`"改为导出 `<StaffDeckApp/>` 纯 React 组件（不再自带 `<html>/<body>`）。
2. **构建改 lib 模式**：vite 输出 ESM（`build.lib`），保留 `base:'/staffdeck-app/'` 让资源路径不变；`scripts/build-staffdeck-app.mjs` 同步调整。
3. **样式作用域化（关键）**：把 Tailwind 全局样式限定在 `.staff-deck-root` 作用域——用 `tailwindcss` 的 `important: '.staff-deck-root'` 或把 StaffDeck 所有类加前缀，避免污染主应用 MUI。
4. **主应用改挂载**：删除 `<iframe>`，改为 `import { StaffDeckApp } from 'staffdeck-app'` 渲染到 `#staffdeck-mount`；保留 `StaffDeckPortal` 的常驻预热逻辑，改为组件的挂载/卸载显隐（去 iframe 后"预热"意义减弱，可简化）。
5. **通信层**：postMessage 协议可原样保留（方案 B 仍能走）；更顺的做法是升级为 props/Context 直传（去掉序列化开销）。
6. **样式回归**：重点验证按钮、布局、z-index、字体在 MUI 容器内无冲突。

---

## 4. 风险与补偿

| 风险（去 iframe 后） | 补偿手段 |
|---|---|
| 失去崩溃隔离 → StaffDeck 报错波及主应用 | 外层包 `<ErrorBoundary>` 兜底 |
| 失去 JS 沙箱 → 全局变量/事件污染 | 约束 StaffDeck 不挂全局、不监听 `document` 级事件 |
| MUI↔Tailwind 样式冲突 | 严格样式作用域化（§3.3）+ 视觉回归测试 |
| 构建耦合 | StaffDeck 经 submodule 软链或独立 npm 包供给主应用解析 |

---

## 5. 结论

"保持现状去 iframe"**可行**，但本质是用工程成本（样式作用域 + 运行时耦合管理）**置换** iframe 的隔离红利。若诉求只是"嵌入更顺滑"，方案 B 最贴合；若诉求是"多端独立部署"，选 A。**在拿到明确诉求前，保留 iframe 是风险最低的选择。**
