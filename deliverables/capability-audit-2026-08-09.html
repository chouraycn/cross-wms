二、重复诊断（按证据）

重复 R1 · openclaw 内置技能三处物理重复（最严重）

id 示例副本 A：引擎 bundled副本 B：工作区直装副本 C：迁移种子

weatherserver/engine/skills/builtin/weatherskills/weatherskills/_imported/openclaw/weather
… (共 52 个)engine ∩ _imported = 52/52；top_direct ∩ _imported = 52/52
证据：server/engine/skills/builtin/ 与 skills/_imported/openclaw/ 各自 52 个 SKILL.md，id 集合 100% 重合；skills/ 下 52 个 id 同时存在于顶层与 _imported/openclaw/ 两处。
风险：① 编辑任一份而漏改其它 → 行为分叉；② db-core.ts 把 _imported/openclaw 迁入 user_skills，与 bundled 形成"双源"，引擎升级后种子不跟随 → 用户看到旧版技能。

重复 R2 · 前端内置技能目录路径错位（二轮更正：误报）

实测未断链：src/types/builtin-skills.ts 位于 src/types/，其 ../../shared/data/builtin-skills.json 经两次 ../ 解析到仓库根 shared/data/builtin-skills.json（非 src/shared/data/）。该文件实际存在且被正常解析，vite.config.ts 也无需 shared 别名。原报告把相对路径算术算错导致误报，此条无需修复。

重复 R3 · 前端 src/skills 重声明 18 个引擎技能

src/skills/ 共 22 个声明式技能，其中 18 个与引擎 builtin 同 id（blucli camsnap clawhub gemini gifgrep github gog imsg notion openhue oracle sag songsee spike tmux trello weather xurl），但采用不同 schema（中文 name + 显式 id + parameters），且目录下无任何实现文件（仅 SKILL.md）。

判定：属"前端展示/工作区级元数据"与"引擎执行级技能"的概念重复。若两者由不同流程维护，会出现 UI 列表与引擎实际可调用集合不一致。

重复 R4 · WMS 业务能力语义重叠（技能 vs 前端能力）

体系②的 WMS 业务技能与体系③的 src/capabilities/warehouse 在"仓库/库存/出入库/在途/体积/指标/报表"主题上高度重叠：

重复 R5 · 双技能框架（TS 引擎 vs Python 数字员工）

体系①的 TS 引擎有完整技能生命周期（loader / discovery / sandbox / workshop / dependency-check / audit）；体系④ StaffDeck 后端 skills/ 又实现了 skill_distiller / skill_editor / skill_reflection / skill_schema 等"技能蒸馏-编辑-反思"框架。两者概念同位但技术栈分裂，数字员工技能无法复用引擎已实现的审计/依赖检查能力。

五、架构收敛决策（P2-6 / P2-7）

R4 收敛：前端业务能力与 WMS 技能的职责边界

现状：src/capabilities/warehouse/（warehouseCapabilityStore + dashboardApi + useWarehouseCapability）与 builtin-* 技能都直连同一批 /api/*。二者并存，职责边界未厘清。

建议（不改动业务逻辑）：以 useWarehouseCapability 作为前端唯一数据层；WMS 技能（builtin-warehouse 等）仅做"意图 → 能力调用"的编排，不在技能文档里重复描述 store 已封装的字段与端点。技能文档只声明"可调用的能力名 + 真实端点契约"（已通过 P0-2 对齐）。避免同一 API 语义在两处漂移。

R5 收敛：双技能框架的治理复用

现状：TS 引擎已有 skill-dependency-checker / skill-audit 等治理能力；StaffDeck 后端 skills/ 另实现蒸馏/编辑/反思框架。概念同位、技术栈分裂。

建议：数字员工侧的技能治理（蒸馏产物校验、反思质量门）复用引擎已实现的 audit / dependency-check，而非两套独立实现。具体可让 StaffDeck 的蒸馏/反思结果回调主引擎的校验入口，统一"技能质量基线"。此项为中长期架构目标，不在本次执行范围。

数据来源：静态扫描仓库 SKILL.md 元信息 + 加载器/迁移脚本/路由挂载源码核对（首轮）；二轮补充 import 解析实证、bundled 目录存在性验证、db-core 迁移分支与 src/skills 引用扫描。建议作为 QA 回归基线，与 tsc/vitest 门禁联动。
