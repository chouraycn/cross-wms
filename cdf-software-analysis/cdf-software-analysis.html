二、架构分析（当前事实）

2.1 统一执行引擎 v9.0

四种执行策略 Legacy / Observer / Planner / ReAct 已统一到单一 streamExecutor（server/engine/streamExecutor.ts 已验证存在）。工具分三类：builtin + plugin + MCP（mcp__{server}__{tool}）；权限分级 auto / confirm / high-risk。这是与旧稿「多策略并存、Planner 已删、Orchestrator 未用」描述的实质演进——策略层已收敛为统一执行入口。

2.2 SSE 流式基础设施

  • 8 个核心事件：init / text / thinking / tool_call / permission_request / done / error / debug；非核心走 sendDebugSSE。
  • 唯一读流原语：src/utils/sse/readSseResponse.ts 已验证存在，所有消费方复用，禁止手写 getReader 循环；必须 decoder.decode() 尾部 flush（否则 UTF-8 汉字流末尾被吞）。
  • error 必走 sendSSE，否则前端卡「思考中」；catch 必发 error+done。

2.3 HTTP 工具执行层（统一安全原语）

server/infra/net/httpToolRequest.ts → executeGuardedHttpRequest()：SSRF 守卫 + DNS 钉扎 + 超时 + JSON 解析 + 50K 截断。两个调用方共享执行层、各留功能层：webTools.ts 的 web_api_call（15s / 禁私网）、staffHttpToolBridge.ts（30s / 允许私网）。铁律：禁止删 staffHttpToolBridge 让 LLM 直接用 web_api_call（token 泄露 + 丢语义化工具名 + 内网不可达）。

2.4 数字员工 StaffDeck 与双套 UI 收敛

  • 代码级收口已完成：删除 39 个 MUI 员工页；/staff /enterprise /workspace → 统一 /staffdeck；tsc --noEmit EXIT=0。localStorage cdfknow.legacyStaffUI 已失效。
  • StaffDeck 前端（shadcn/Tailwind，StaffDeck-main/，2,920 文件 / 687K 行）经 iframe 嵌入，由 StaffDeckPortal.tsx 提升到路由树外常驻；<Route path="/staffdeck" element={null}/> 是有意设计（避免 remount 二次白屏），禁改。
  • 响应剥包：server/index.ts:394-419 中间件对 /api/staffdeck/* 且 code===0 剥包；错误响应保留 envelope。SSE 事件名必须用 StaffDeck 前端原生名（session_created / stream_delta / status{phase:'tool'} / stream_end+done），否则聊天假死。

2.5 API 契约对齐（P2-1）

已收口 6 批 / 25 文件 / 251 调用（人工逐文件，codemod 不可靠，禁止依赖）。核心规则：Express 路由处理器从裸 res.json(X) 迁移到统一 API 信封。eslint 须 0 error，且需排查局部 const ok 遮蔽导入导致的运行时崩溃。

3.2 已知风险与铁律（须遵守，违反即出事）

P0 级运行期陷阱（已验证会致白屏 / 502 / 崩溃）

  • Vite 扩展名解析坑：默认 resolve.extensions 中 .ts 在 .tsx 前。无扩展名 import 一个只有 .tsx 的模块会先请求 .ts 得 404 → 模块加载失败 → 整页白屏。tsc 通过 ≠ Vite 运行时能解析。铁律：含 JSX 的模块用 .tsx 且 import 显式带 .tsx；改完必用浏览器/Playwright 实跑确认非白屏。
  • ESM js-yaml 加载坑：禁 import yaml from 'js-yaml'（5.2.2 ESM-only 无 default → SyntaxError → 全部 API 502）；必须 import * as yaml。
  • WKWebView 兼容：禁 CSS @keyframes（用 inline transition）；禁 requestAnimationFrame（用 setTimeout(fn,16)）。frameless 红黄绿圆点在 WindowDragBar.tsx，禁改按钮逻辑与 pywebview_app.py Api。

构建 / 提交 / Git 铁律

  • 提交前 NODE_OPTIONS=--max-old-space-size=8192 tsc --noEmit（默认小堆 OOM exit 137）；vite build 须绿。
  • pre-commit 钩子陷阱：跑 lint-staged + 全量 tsc（200 万行→OOM/极慢）+ tsc -p server/tsconfig.json（fork 既有错误必 fail）。修复：钩子改用 tsgo 增量（typecheck:fast）或仅 lint-staged；当前靠 git commit --no-verify 绕过，门禁失效。
  • 提交必须精确列文件名 add，禁 git add -A；.workbuddy/ 被 gitignore，但 MEMORY.md 已跟踪——混进 git add 会报 ignored 让整条命令失败。
  • .npmrc 需 legacy-peer-deps=true；DMG 验证 grep -c "关键字符串" server_dist/index.cjs。
  • 本地分支无 upstream，推送须 git push -u origin <branch>；git pull --rebase 后须 git show HEAD:<关键文件> 验证关键改动未被静默改写。
  • git stash 恢复坑：多 stash 下裸 git stash pop 易戳错。铁律：pop 前 git stash show --name-only stash@{N} 确认；恢复用 checkout stash@{N} -- <files> 而非 pop。

治理与质量

  • codemod 不可靠（2026-08-11）：multiline 裸对象截断丢 {；局部 const ok 遮蔽导入→运行时崩溃。API 信封迁移必须人工逐文件 + eslint 0 error + 查 ok 冲突。
  • knip 不可信：ignoreFiles 含 scripts/** 未覆盖 extensions/ → 「Unused dependencies」列表不可信、不可盲删；删依赖前须手动核验 extensions/ scripts/ build-server.mjs external、dist 产物。
  • 工作区不洁：2,754 modified + 395 untracked + openclaw/ StaffDeck-main/ 子模块 drift，须作为后续清理前置项。
  • engine 测试隔离阻塞：851 unresolved imports 阻塞（须 CI 先 build openclaw）。

四、技术债务

状态管理未收敛

Context + Zustand + useState 三种并存，ChatContext 过于庞大。旧稿建议「统一 Zustand + 原子化」仍未落地。

大文件维护困难

server/engine/toolRegistry.ts ~2,201 行、server/routes/chat.ts ~2,200 行、ChatMessageList.tsx ~2,112 行。单一文件过大。

pre-commit 门禁失效

钩子跑全量 tsc → OOM/慢 + fork 既有错误 fail；当前靠 --no-verify 绕过。应切 tsgo 增量。

构建产物管理

server_dist/ dist/ 被 git 跟踪又是构建产物，应加 .gitignore、CI 重建。

4.1 代码层面

  • 魔法数字：多处硬编码超时（5s / 30s）、重试次数、阈值，应提取为配置。
  • 重复代码：前端多页面相似表格/表单逻辑，可提取通用组件。
  • any 类型滥用：多处 any 绕过类型检查，应逐步替换。
  • 错误处理不一致：try/catch、.catch()、不处理三者混用。
  • 测试质量参差：943 测试文件但覆盖不均，engine 测试占 57%，应用层核心逻辑仍薄。
